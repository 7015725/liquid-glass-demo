# 触发器匹配模式与重复触发策略

本文描述规则级触发器行为的持久化字段、运行时语义和默认值。旧数据没有这两个字段时分别按
`ANY` 和 `DROP` 处理，行为与 0.7.x 相同。

## 触发器匹配模式

字段：`Rule.triggerMatch`（UI 模型为 `Cmd.triggerMatch`）。

- `ANY`（默认）：任一触发器命中即执行。事件型触发器仍按各自的状态边沿、参数和 2 秒防抖判断。
- `ALL`：规则的所有触发器都满足才执行。
  - **状态型触发器**按命中事件发生时的**当前状态**判断，不要求看到一次状态边沿：
    - WiFi：`connected` 表示当前网络为 WiFi 且（配置了 SSID 时）SSID 一致；
      `disconnected` 表示当前 SSID 不是配置的那个（未配置 SSID 时表示当前不是 WiFi）。
      系统不给出 SSID（未授权、定位关闭或 `<unknown ssid>`）时，带 SSID 的两个方向都不匹配，
      避免把「不知道」当成「不是 Home」。
    - 充电状态：`trigger.power_connected` / `trigger.power_disconnected` 按当前是否充电判断；
      旧版 `trigger.charging` 的 `charging` / `stopped` 也按当前充电状态判断。
    - 电量：按当前电量与阈值比较；旧版 `battery_low` 按“低于阈值”处理。
      方向「任意变化」是**事件型**，不按当前电量判断；它只受 30 秒冷却和 2 秒防抖限制。
    - 亮屏 / 熄屏属于**事件型**：ALL 模式要求它们在窗口内都发生过，不能同时按当前状态满足。
  - **事件型触发器**要求在有效窗口内都至少发生过一次。窗口来自
    `triggerMatch.windowSeconds`，默认 60 秒，编辑页提供 30 秒 / 60 秒 / 5 分钟快捷值。
  - 窗口从每次命中事件的时间戳计算；窗口外的旧事件不会参与匹配。
  - 一次成功执行会消费该规则的窗口内事件记录，下一次必须重新满足全部条件。
  - 状态型触发器没有历史边沿要求，因此只含状态触发器的规则在任一相关事件到达时按当前状态判断。
  - 不支持监听、参数无效或没有事件的触发器不会让 `ALL` 规则误触发。
  - 系统广播类触发器全部按事件型处理，详见 [`system-broadcast-triggers.md`](system-broadcast-triggers.md)。

## 重复触发策略

字段：`Rule.runMode`（UI 模型为 `Cmd.runMode`）。

- `DROP`（默认）：规则正在运行时，新的触发直接丢弃。
- `QUEUE`：规则正在运行时把触发放入队列，当前运行结束后依次启动；每个规则最多排队
  **10** 次，超过上限的触发丢弃。队列中的触发保留触发时的 reason 和事件变量。
- `RESTART`：新的触发先取消当前运行，再启动新运行。取消通过宿主的执行 Job 完成；已经
  进入执行器的步骤会在下一个协作取消检查点停止，不再写入新的执行记录。
- `PARALLEL`：允许同时运行，每个规则最多 **3** 个实例，超过后丢弃。并行运行仍各自拥有
  独立的执行日志、变量上下文和停止入口。

## 持久化与兼容

- `Rule.triggerMatch` 和 `Rule.runMode` 已存在于 v3 文档；本阶段补齐执行语义和编辑器入口。
- 旧文档缺省字段由 Kotlin 默认值补齐；`RuleDocumentMapper` 在 UI 模型与 engine 模型之间
  双向保留这两个字段。
- 队列上限、并行上限和 2 秒防抖是运行时保护值，不写入文档，便于以后调整而不迁移数据。

## 测试重点

- `ANY` 保持旧行为；`ALL` 覆盖状态型、事件型和混合触发器以及窗口过期。

- 四种策略覆盖空闲、运行中、队列上限、并行上限、重启取消和队列唤醒。

## 地点触发与系统定位开关

地点触发器在宿主存活期间监听 `LocationManager.PROVIDERS_CHANGED_ACTION`。启动时系统定位关闭、或在运行中
被关闭时，watcher 不会留下「已监听」的假象；用户重新打开定位后会恢复请求。每次恢复仍按网络定位优先、
GPS 次之，采样间隔两分钟，不申请后台定位权限。
